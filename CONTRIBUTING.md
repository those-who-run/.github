# Contributing

Thanks for looking. Those Who Run is a personal project, built in the open, mostly in small milestones planned in [`paddock`](https://github.com/those-who-run/paddock). Issues and pull requests are welcome, but there's no promise they'll be picked up quickly.

v2 is built across several repositories, one per component, beside v1 ([those-who-run/those-who-run](https://github.com/those-who-run/those-who-run)), which is in maintenance from 1.0.0. This guide applies to every repository in the organisation that has none of its own.

## Before you start

- **Issues are opened only in [`paddock`](https://github.com/those-who-run/paddock/issues), whichever repository they concern.** The component repositories have Issues turned off, so every issue, milestone and label is in one place. An issue's `component:` label says which repository the change lands in. v1 is in maintenance: while its repository has Issues open, a v1 bug can be reported there.
- **Read the issue format.** Every issue is a spec: paddock's [`docs/ISSUE_FORMAT.md`](https://github.com/those-who-run/paddock/blob/main/docs/ISSUE_FORMAT.md). Open it from one of paddock's templates. A bug report needs what happened, when, the component and its version, and the evidence.
- **New issues wait for triage.** Every template adds the `needs triage` label, and the maintainer removes it when the issue is accepted as a spec. Nobody works on an issue until then.
- **Talk first for anything big.** Open an issue before a large change, so we can agree the approach.
- **Decisions that affect several issues** are recorded as ADRs in paddock's [`docs/adr/`](https://github.com/those-who-run/paddock/tree/main/docs/adr).
- **Security problems are never a public issue.** Report them privately, as the [security policy](https://github.com/those-who-run/.github/blob/main/SECURITY.md) says.

## Making a change

- One issue, one pull request, in the repository of the component it changes. The pull request says `Closes those-who-run/paddock#N.` only when every acceptance criterion is met, and `Part of those-who-run/paddock#N` otherwise.
- Each repository's `AGENTS.md` says how to build and check it, and the command that matches CI must be green. The rules every v2 repository shares are in paddock's [`AGENTS.md`](https://github.com/those-who-run/paddock/blob/main/AGENTS.md).
- Telemetry behaviour is pinned by recordings of real drives: v1's [`tests/fixtures/`](https://github.com/those-who-run/those-who-run/tree/main/tests/fixtures) and the drives in [`outings`](https://github.com/those-who-run/outings). A change to what the engineer says or detects comes with a fixture.
- Docs change in the same pull request as the code they describe.
- Commits and pull request titles follow [Conventional Commits](https://www.conventionalcommits.org/) (`feat:`, `fix:`, `docs:` …). Releases are cut from them.
- Write in British English, in plain sentences.

## Using AI tools

AI help is fine. Say which tool helped and how, in the pull request or issue: a `Co-Authored-By:` or `Assisted-by:` trailer on the commits, or a line in the description. Either way, you are responsible for every line: you must understand it, be able to explain it, and have run the repository's checks yourself. Security reports must be reproduced by you, not only generated by a tool. Pull requests and reports that look generated and unreviewed may be closed without review.

The project itself is largely written with Claude Code and reviewed by the maintainer. The rules the agents follow are in paddock's [`AGENTS.md`](https://github.com/those-who-run/paddock/blob/main/AGENTS.md), and people are welcome to use them too.
